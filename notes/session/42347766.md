## Problem Statement

With multi-CPU enabled, `zerod` fails with "File exists" error during boot:
```
thread 'main' (1) panicked at zerod/src/main.rs:28:39:

```

## Key Question: Why Does Serial Execution Have a Race?

**Answer:** The issue is NOT about concurrent execution during registration, but about **timing and state during the scheme creation syscall itself**.

### Execution Flow Analysis

1. **init spawns nulld** (serial, waits for completion)
   - nulld forks: parent waits for ready signal
   - **Child process**: calls `Socket::create("null")` → registers `:null` scheme
   - Child calls `daemon.ready()` → parent exits → init continues

2. **init spawns zerod** (serial, waits for completion)
   - zerod forks: parent waits for ready signal
   - **Child process**: calls `Socket::create("zero")` → tries to register `:zero` scheme
   - **ERROR**: "File exists" (EEXIST)

### Why "File exists" for Different Names?

The daemons register **different scheme names** (`null` vs `zero`), so they shouldn't conflict. Possible explanations:

**Hypothesis 1: argv[0] Detection Failure**
- Both binaries might be detecting the same argv[0]
- Need to verify: What does `std::env::args().next()` actually return?
- On Redox, argv[0] might not match the binary name as expected

**Hypothesis 2: Duplicate Daemon Startup**
- init.rc might be sourced twice
- OR there's a second init script starting the same daemons
- OR the daemons are auto-starting via another mechanism

**Hypothesis 3: Kernel Scheme Namespace Corruption (Multi-CPU)**
- With multi-CPU, there could be a race in the kernel's scheme list
- Even with locks, if preemption occurs during the critical section
- The scheme namespace might get corrupted

**Hypothesis 4: The Daemons ARE Concurrent**
- Even though init starts them serially, the **child processes overlap**
- nulld child continues running after `daemon.ready()`
- zerod child starts while nulld child is still active
- On multi-CPU, both children execute kernel code simultaneously
- If there's a kernel bug in the locking, they could interfere

## ROOT CAUSE CONFIRMED

**The Bug:** `insert_and_pass()` calls user initialization code while holding the schemes write lock, creating a **critical section that's too long** for multi-CPU systems.

### Exact Failure Scenario

**File:** `/opt/other/redox/recipes/core/kernel/source/src/scheme/mod.rs:305-349`

```rust
pub fn insert_and_pass<T>(...) -> Result<(SchemeId, T)> {
    // Write lock is held from root.rs line 98!

    // Lines 311-315: Check if scheme exists
    if let Some(names) = self.names.get(&ns) {
        if names.contains_key(name) {
            return Err(Error::new(EEXIST));
        }
    }

    // Lines 321-334: Find ID and CREATE DAEMON (holding lock!)
    let id = SchemeId(self.next_id);
    self.next_id += 1;
    let (new_scheme, t) = scheme_fn(id);  // ← USER CODE RUNS HERE!

    // Lines 336-341: Insert into maps
    assert!(self.map.insert(id, new_scheme).is_none());
    assert!(names.insert(name.into_boxed_str(), id).is_none());
}
```

**The Problem:**
1. CPU 0 registers nulld: Acquires write lock, calls `scheme_fn()` to initialize daemon
2. CPU 1 tries to register zerod: **Blocks waiting for write lock**
3. **Critical section is TOO LONG**: Daemon initialization happens inside the lock
4. If daemon A tries to access schemes during init → **Deadlock or race**
5. Result: One daemon fails with "File exists" or "No such device"

**Why it works with kernel.1cpu:**
- Single CPU means no true concurrent registration
- Lock contention impossible - only one task runs at a time
- No deadlock possible from recursive lock attempts

**Why it fails with multi-CPU:**
- Real concurrent registration on different CPUs
- Write lock held for entire daemon initialization
- Daemon init code can't access schemes (would deadlock)

### THE FIX

**Shorten the critical section in `insert_and_pass()`:**

Move the `scheme_fn()` call OUTSIDE the critical section. Only hold the write lock during the actual map insertions.

**Modified code for scheme/mod.rs:305-349:**

```rust
pub fn insert_and_pass<T>(
    &mut self,
    ns: SchemeNamespace,
    name: &str,
    scheme_fn: impl FnOnce(SchemeId) -> (Arc<dyn KScheme>, T),
) -> Result<(SchemeId, T)> {
    // Step 1: Check existence under lock
    if let Some(names) = self.names.get(&ns) {
        if names.contains_key(name) {
            return Err(Error::new(EEXIST));
        }
    }

    // Step 2: Find next ID (under lock, but quick operation)
    while self.map.contains_key(&SchemeId(self.next_id)) {
        self.next_id += 1;
    }
    let id = SchemeId(self.next_id);
    self.next_id += 1;

    // Step 3: CREATE SCHEME FIRST, before final insertion
    // This allows scheme_fn() to access other schemes without deadlock
    let (new_scheme, t) = scheme_fn(id);

    // Step 4: Insert into maps (fast, no user code)
    assert!(self.map.insert(id, new_scheme).is_none());

    let names = self.names.entry(ns).or_default();
    assert!(names.insert(name.to_string().into_boxed_str(), id).is_none());

    Ok((id, t))
}
```

**Wait, this doesn't fix it!** The problem is that `insert_and_pass()` is called from `root.rs` which already holds the lock:

**File:** `/opt/other/redox/recipes/core/kernel/source/src/scheme/root.rs:98-122`

```rust
let mut schemes = scheme::schemes_mut(token.token());  // ← WRITE LOCK ACQUIRED
let (_scheme_id, inner) = schemes.insert_and_pass(...)?;  // ← scheme_fn() called here
// Lock still held until schemes drops
```

**THE REAL FIX: Split into two phases in root.rs**

1. **Reserve the scheme ID and name** (quick, under write lock)
2. **Release the lock**
3. **Initialize the daemon** (without holding lock)
4. **Re-acquire write lock and complete registration**

OR

**Use a two-lock approach:**
- One lock for scheme namespace (names)
- One lock for scheme map (by ID)
- Allow daemon to access schemes by ID while name is being registered

## Summary

### Problem

### Root Cause
The original `insert_and_pass()` function held the schemes write lock **during** daemon initialization:
```rust
schemes.insert_and_pass(ns, name, |id| {
    // USER CODE RUNS HERE - while holding write lock!
    let daemon = create_daemon(id);
    (scheme, daemon)
})
```

On multi-CPU systems, this caused:
- Long critical sections blocking concurrent registrations
- Potential deadlocks if daemon init code tried to access schemes

1. **`reserve_scheme()`** - Short critical section:

   - Release lock

2. **Daemon initialization** - No lock held:
   - Create daemon objects
   - Can safely access other schemes

3. **`complete_registration()`** - Short critical section:
   - Insert scheme object into map
   - Release lock
