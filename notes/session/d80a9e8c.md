## Key Question: Why Does Serial Execution Have a Race?

**Answer:** The issue is NOT about concurrent execution during registration, but about **timing and state during the scheme creation syscall itself**.

### Execution Flow Analysis

1. **init spawns nulld** (serial, waits for completion)
   - nulld forks: parent waits for ready signal
   - **Child process**: calls `Socket::create("null")` → registers `:null` scheme
   - Child calls `daemon.ready()` → parent exits → init continues

2. **init spawns zerod** (serial, waits for completion)
   - zerod forks: parent waits for ready signal
   - **Child process**: calls `Socket::create("zero")` → tries to register `:zero` scheme
   - **ERROR**: "File exists" (EEXIST)

### Why "File exists" for Different Names?

The daemons register **different scheme names** (`null` vs `zero`), so they shouldn't conflict. Possible explanations:

**Hypothesis 1: argv[0] Detection Failure**
- Both binaries might be detecting the same argv[0]
- Need to verify: What does `std::env::args().next()` actually return?
- On Redox, argv[0] might not match the binary name as expected

**Hypothesis 2: Duplicate Daemon Startup**
- init.rc might be sourced twice
- OR there's a second init script starting the same daemons
- OR the daemons are auto-starting via another mechanism

**Hypothesis 3: Kernel Scheme Namespace Corruption (Multi-CPU)**
- With multi-CPU, there could be a race in the kernel's scheme list
- Even with locks, if preemption occurs during the critical section
- The scheme namespace might get corrupted

**Hypothesis 4: The Daemons ARE Concurrent**
- Even though init starts them serially, the **child processes overlap**
- nulld child continues running after `daemon.ready()`
- zerod child starts while nulld child is still active
- On multi-CPU, both children execute kernel code simultaneously
- If there's a kernel bug in the locking, they could interfere
