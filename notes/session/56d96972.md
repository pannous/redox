### The Real Problem: Page Table Activation

After extensive testing, I've determined the issue is **NOT** timer interrupts, interrupts, or PAN - it's that **userspace memory isn't accessible** when `usermode_bootstrap` runs.

### Conclusive Evidence

**Even a 1-byte copy hangs:**
```
copy_from_slice: Testing with 1-byte copy first...
[HANGS - no return, no exception]
```

**What this proves:**
1. ✗ Not a performance issue (single byte hangs)
2. ✗ Not a PAN/privilege issue (STTR also hangs)
3. ✗ Not alignment (byte stores hang)
4. ✗ Not missing barriers (DSB/ISB doesn't help)
5. ✓ **Pages at 0x1000 simply aren't mapped/accessible**

### Root Cause Hypothesis

The bootstrap context's **user page tables are not active** when `usermode_bootstrap` runs. The `mmap` operation allocates pages in the bootstrap's address space, but we're still using the kernel's page tables (TTBR1_EL1), where those user pages don't exist.

**What should happen:**
1. Context switch to bootstrap context
2. Activate bootstrap's address space (switch TTBR0_EL1)
3. User pages at 0x1000+ become accessible
4. arch_copy_to_user succeeds

**What's actually happening:**
1. Context switch to bootstrap context ✓
2. Address space NOT activated (still using kernel page tables) ✗
3. User pages don't exist in active page tables ✗
4. Stores hang waiting for pages that don't exist ✗

### Files Modified & Committed

1. **Exception handlers** - Added comprehensive logging (never triggered)
2. **arch_copy_to_user** - Tested multiple strategies (all hang)
3. **Analysis document** - `notes/arch_copy_hang_analysis.md`
4. **Debug logging** - Throughout boot and copy process

All committed to `ap-boot-identity-mapping` branch.

### Next Steps to Fix

1. Check if context switch activates the address space's page tables
2. Verify TTBR0_EL1 is switched during context switch
3. Add explicit page table activation before `usermode_bootstrap`
4. Or defer bootstrap loading until after entering userspace (EL0)

This is a critical but solvable issue - we just need to ensure the correct page tables are active before attempting kernel→user memory copies.
