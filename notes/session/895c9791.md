## The Problem is Architectural (General Solution is Feasible)

The hang isn't driver-specific bugs per se - it's **missing timeout/cancellation infrastructure** in the kernel. The root causes:

| Level | Issue | Fix Difficulty |
|-------|-------|----------------|
| **Scheme locks** | No timeout on global schemes lock acquisition | Medium |
| **User scheme calls** | `call_extended_inner()` blocks forever waiting for driver response | Hard |
| **Root scheme enumeration** | Double lock acquisition without timeout | Medium |
| **No health checking** | Dead drivers aren't detected/removed | Medium |

## Why `ls /scheme/` is the Canary

It's uniquely vulnerable because it:
1. Acquires multiple locks
2. Iterates **all** schemes in namespace
3. Any single hung driver blocks the entire operation

## General Solutions (Feasible but Non-Trivial)

1. **Add timeouts to user scheme calls** (`user.rs:call_extended_inner()`)
   - Return `ETIMEDOUT` after N seconds if driver doesn't respond
   - ~200 lines of kernel code

2. **Async scheme enumeration** 
   - Skip unresponsive schemes instead of blocking
   - Mark them with `?` or similar in listing

3. **Driver health watchdog**
   - Periodic ping to user schemes
   - Auto-unregister unresponsive ones

4. **Non-blocking lock acquisition**
   - `try_lock()` with timeout instead of blocking `lock()`

## My Assessment

**General solution: Feasible, but requires kernel changes**

The cleanest fix would be option 1 (timeouts in `user.rs`) - it's the single choke point. This would make `ls /scheme/` return `ETIMEDOUT` for stuck drivers instead of hanging forever.
