## Summary

I've debugged curl in Redox and found the root cause is a **timing/event delivery issue**, not a packet transmission problem.

### Key Findings:

1. **Network packet flow is working correctly:**
   - TCP SYN is sent successfully (66 bytes)
   - TCP SYN-ACK arrives only **70ms later** (very fast!)
   - smolnetd properly receives and processes the SYN-ACK

2. **The problem is timing:**
   - curl makes ~10 rapid TCP scheme calls checking connection status
   - curl gives up with "Connection timed out" **before** the SYN-ACK arrives
   - The SYN-ACK arrives ~70ms after the SYN, but curl has already given up

3. **Timeline from debug:**
   ```
   53.988s - TCP SYN sent
   53.988s-54.0XXs - curl makes ~10 on_tcp_scheme_event calls
   54.0XXs - curl reports "Connection timed out" 
   54.058s - TCP SYN-ACK arrives (only 70ms later!)
   ```

### Root Cause Analysis:

The issue is **event delivery** - curl is not properly waiting/blocking for connection completion. Instead of receiving fevent notifications when TCP state changes, it's making rapid non-blocking checks and giving up too quickly.

This explains why ping also has issues - responses arrive but the application has already given up.

### What to investigate next:
1. How relibc/curl implements connect() and checks for completion
2. Whether smolnetd's fevent notifications are being sent correctly
3. Whether there's a timeout configuration that's too short

I've documented all findings in `/opt/other/redox/notes/networking.md`.
