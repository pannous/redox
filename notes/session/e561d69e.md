**Summary: set-background tool created**

I've created a `set-background` tool at `recipes/core/base/source/set-background/` that:

**What it does:**
- Decodes PNG images (RGB, RGBA, Grayscale, GrayscaleAlpha formats)
- Attempts to open display schemes (virtio-gpu, vesa) 
- Maps a DRM dumb framebuffer and copies the image centered
- Uses the graphics-ipc V2GraphicsHandle for framebuffer operations

**Testing results:**
- PNG decoding works: `set-background: decoded PNG 1024x768 Rgb`
- Image loading works: `set-background: loaded image 1024x768 (786432 pixels)`
- **Display access fails**: `Error: no display scheme found`

**The challenge:**
The display scheme in Redox is managed through inputd's VT (Virtual Terminal) system. Looking at the boot log, display paths like `/scheme/display.virtio-gpu/v2/1` are created for specific VTs, and fbcond claims VTs 1 and 2. 

To draw directly to the display without going through Orbital, userspace programs need to:
1. Request a VT from inputd using `ConsumerHandle::new_vt()`
2. Get a display handle via `input_handle.open_display_v2()`

This is how fbcond does it. A standalone background-setter would need to integrate with the inputd/VT system rather than directly opening display schemes.

**The code is committed and built.** The release binary is at `/opt/other/redox/share/set-background-release` (2.8MB).

Would you like me to:
1. Modify set-background to integrate with inputd's VT system (like fbcond does)?
2. Create a simpler approach that runs during boot before fbcond claims the display?
3. Explore other ways to draw to the screen?
