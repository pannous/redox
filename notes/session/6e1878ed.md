## What "Bypassing Normal Recipe System" Means

**Normal Redox build flow:**
```
config/base.toml → recipe.toml → cookbook → .pkg → redoxfs image
```

The cookbook system:
1. Reads package lists from config/*.toml
2. Finds recipe.toml for each package
3. Downloads/extracts source
4. Runs build commands (typically cargo with LLVM)
5. Stages to .pkg files
6. Assembles into filesystem

**Your Cranelift build flow:**
```
build-cranelift.sh → direct cargo+cranelift → manual injection into image
```

It bypasses because:
- Uses Cranelift backend instead of LLVM (different target spec)
- Compiles directly without cookbook orchestration
- Injects binaries manually (mount/copy/umount)
- No .pkg intermediate format

## Can We Integrate?

Yes, but there are tradeoffs:

| Approach | Pros | Cons |
|----------|------|------|
| **Keep separate** | Simple, working now, full control | Manual injection, no package management |
| **Wrap in recipes** | Uses existing infra, cleaner | Recipe system assumes LLVM toolchain |
| **Hybrid** | Best of both - cranelift recipes | Requires cookbook modifications |

## Recommendation

**Keep separate for now** - the recipe system is tightly coupled to the LLVM toolchain. Integrating would require modifying cookbook's build logic to support alternate backends.

However, you could **document the cranelift targets as pseudo-recipes** in `notes/` so there's a clear mapping of what build-cranelift.sh builds and where outputs go. This gives discoverability without the integration burden.
